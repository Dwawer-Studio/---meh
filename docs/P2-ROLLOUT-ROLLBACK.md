# خطة طرح ورجوع P2

## المتطلبات السابقة

- P2 engineering gate أخضر من SHA المرشح.
- `P2-H01` و`P2-H02` في soft launch، وPITR `P2-O01` مجرب.
- dashboards والتنبيهات وحارس الجوائز يعملون.
- العميل القديم يستطيع الودي عبر PeerJS، لكنه لا يمنح نتيجة/تاماشي موثوقة.

## الشرائح

```text
فريق داخلي → 5% منطقة واحدة → 25% → 50% → 100% المنطقة → منطقة ثانية
```

مدة soak لكل شريحة هي الأكبر من 3× p95 مدة الجلسة أو المدة اللازمة لحجم عينة
MCR المقفل. لا توسع لمجرد مرور ساعة بلا traffic كافٍ.

## حواجز التوقف

- desync واحد مؤكد.
- MCR أو crash-free دون بوابة P2.
- p95 ACK فوق الحد المقفل، أو queue depth ينمو دون عودة.
- حذف حساب أو استعادة مقعد أو نسخة احتياطية يفشل.
- العميل القديم يدخل حلقة reconnect أو يرى حالة لا يفهمها.

## الرجوع

1. ثبت النسبة ولا ترسل مستخدمين جددًا.
2. عند عطل اعتمادية فقط، drain للغرف السليمة ثم عطّل
   `authoritative_service` في release config.
3. عند نزاهة/تسريب، أغلق الغرف المتأثرة فورًا وجمّد النتائج الاقتصادية.
4. يعود زر الودي إلى PeerJS. تعرض الخدمة رسالة صيانة للـquick play؛ لا تدعي
   أن PeerJS بديل آمن للجوائز.
5. احتفظ بالـschema، وانشر إصلاح forward. استرجاع الكود لا يحذف أعمدة أو action
   logs.
6. قبل إعادة الطرح، أعد replay للحادث واختبار regression ثم ابدأ من 5%.
