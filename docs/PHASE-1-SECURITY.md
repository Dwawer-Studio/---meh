# المرحلة 1 — الأمان ومصداقية رسائل الشبكة

## النطاق

تعالج هذه المرحلة البنود `SEC-01` و`NET-01` و`NET-02` و`NET-03` المسجلة
في خط الأساس. يبقى نموذج الثقة المعتمد للنسخة الحالية أن المضيف يدير حالة
المباراة، لكن أي رسالة أو قيمة قادمة عبر PeerJS تُعامل كمدخل غير موثوق قبل
استخدامها.

## الإصلاحات المنفذة

### DOM والبيانات غير الموثوقة

- استبدال بناء الردهة وملفات الأعضاء وبديل صورة البطاقة بعناصر DOM تستخدم
  `textContent` و`replaceChildren`.
- عدم إدخال أسماء اللاعبين أو الصور الرمزية أو أسماء البطاقات في `innerHTML`.
- تقييد الصور الرمزية بالقائمة المحلية المعتمدة، والأسماء إلى 24 محرفًا بلا
  محارف تحكم.
- إعادة بناء بطاقات الحالة الشبكية من كتالوج الرزمة المحلي؛ لا تُستخدم روابط
  الصور أو الأنواع أو الإيموجي القادمة من الشبكة.
- رفض حالات اللعبة ذات المعرّفات المكررة أو القيم والأعداد والاتجاهات غير
  الصالحة.
- إضافة بصمة SRI ‏`sha384` إلى ملف PeerJS المثبت على الإصدار `1.5.4` وتفعيل
  قاعدة `require-sri` لكل مورد خارجي.
- إزالة خط Google Fonts الخارجي واستخدام خطوط النظام، بحيث لا يبقى مورد CSS
  خارجي غير قابل للتثبيت ببصمة ثابتة.

### الحركات والاختيارات

- لا يُلغى مؤقت الدور إلا بعد التحقق من هوية المقعد ومعرّف البطاقة وصلاحية
  الرمية. الحركة غير الصالحة تترك المؤقت والحالة كما هما.
- كل طلب اختيار بعيد يحمل `promptId` متزايدًا ويرتبط باللاعب المقصود.
- تُرفض الإجابات القديمة، وإجابات لاعب آخر، والقيم غير الصالحة للون أو الخيار
  أو الهدف دون استهلاك الطلب الحالي.

### الانضمام وحدود الغرفة

- كود الغرفة مقيد بخمسة محارف من الأبجدية التي يولدها التطبيق.
- الحد الأقصى أربعة لاعبين شاملًا المضيف.
- الاتصال الخامس يُزال من قائمة البث قبل إغلاقه ويستلم سبب رفض واضحًا.
- الانضمام بعد بدء المباراة مرفوض.
- الرفض والإغلاق idempotent للاتصال نفسه، لمنع سباق حدث الاتصال مع رسالة
  `hello`.
- العميل يعرض رسائل محلية واضحة للغرفة الممتلئة أو المباراة التي بدأت.

## تحقق المتصفح الحقيقي

شُغّل الفرع الحالي محليًا عبر `npm run serve` واختُبر في نوافذ مستقلة:

1. إنشاء غرفة وانضمام عميل ومزامنة اسمي الردهة والبطاقات.
2. تنفيذ حركة سحب للمضيف: اليد من 7 إلى 8.
3. تنفيذ حركة سحب للعميل: اليد من 7 إلى 8، وظهر العدد 8 فورًا عند المضيف.
4. إنشاء غرفة بأربعة لاعبين ثم محاولة إدخال لاعب خامس؛ بقي عدد الردهة 4
   وظهرت رسالة «الغرفة ممتلئة» للخامس.
5. محاولة الانضمام بعد بدء المباراة؛ بقي العميل في شاشة الأونلاين وظهرت رسالة
   «بدأت المباراة بالفعل» بصورة مستقرة.
6. سجلات المتصفح للمضيف والعملاء: 0 أخطاء و0 تحذيرات.

## حدود هذه المرحلة

- لا تقدم PeerJS مصادقة مشفرة لهوية بشرية، ولا تمنع المضيف الموثوق من تعديل
  حالة لعبته؛ هذه ليست منصة تنافسية ذات خادم تحكيم.
- انقطاع الاتصال، إعادة الاتصال، واستكمال المباراة بعد تعطل الشبكة ضمن المرحلة 2.
- عدالة التأثيرات وحفظ مجموع بطاقات الرزمة ضمن المرحلة 3.
