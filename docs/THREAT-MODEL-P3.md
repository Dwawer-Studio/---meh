# نموذج تهديد P3 — المجلس العائد

التاريخ: 2026-08-28

## الأصول وحدود الثقة

الأصول هي موافقة العضوية، أسماء وهوية المجالس، سجل الجلسات، الدعوات والتذكيرات،
عبارات الدردشة، الكتم المحلي، البلاغات، والرموز التحليلية. العميل غير موثوق؛
الخادم وقاعدة PostgreSQL هما المرجع للعضوية وربط الغرفة وتسجيل النتيجة. مسارات
`/internal/moderation/*` حد تشغيل loopback ولا يجوز نشره.

لا توجد جهات اتصال، رسائل حرة، قائمة عالمية، اقتصاد، أو بيانات بطاقات جديدة في
P3. تعريفات البطاقات وآرت اللعبة وقواعد الفوز خارج النطاق ولم تتغير.

## التهديدات والضوابط

| التهديد | الأثر | الضبط المنفذ | المتبقي/التشغيل |
|---|---|---|---|
| IDOR على مجلس | كشف أعضاء/نتائج أو دخول غرفة | كل list/detail/schedule/reminder وربط غرفة يتحقق من عضوية active | راقب `MAJLIS_MEMBERSHIP_REQUIRED` دون تسجيل الاسم |
| إضافة لاعب بلا رضاه | spam أو انتحال علاقة | المالك وحده عضو عند الإنشاء؛ القبول يتطلب حسابًا كان مقعدًا بشريًا في source room | لا دعوات contacts ولا bulk add |
| سباق إنشاء مجلسين من غرفة | تفرع هوية المجموعة | فهرس فريد `source_room_id` ومعاملة ذرية وربط دائم للغرفة | الخطأ يعاد بصورة قابلة للاسترجاع |
| تزوير/خداع اسم المجلس | UI spoofing | NFKC، حد 32، منع control/bidi overrides، إخراج DOM بـ`textContent`، قائمة cosmetics مسموحة | مراجعة إساءة الاسم ضمن دعم الحساب |
| دخول غير عضو عبر room code | كشف مجلس خاص | `create/join` المرتبطان بالمجلس يتحققان خادميًا من العضوية | room code ليس صلاحية عضوية |
| spam أو حقن عبر الدردشة | إساءة/XSS | ست عبارات ثابتة فقط، allowlist خادمية، cooldown 4s، لا free text | العلم يعطل السطح فورًا |
| تجاوز الكتم | استمرار الأثر عند جهاز اللاعب | الكتم يوقف عرض أحداث seat المحدد محليًا فورًا | الكتم لجلسة الطاولة؛ الحظر الدائم مرحلة سياسة لاحقة |
| بلاغ ذاتي/بوت/مكرر/خاص | تسميم الطابور | بشري ضد بشري، match وطاولة عامة مطلوبان، سبب allowlist وقيد تكرار | إساءة البلاغ تراجع تشغيليًا ولا تكشف المُبلّغ |
| كشف طابور البلاغات | بيانات سلوكية وحسابات | endpoint loopback ورمز مشغّل مستقل إلزامي في الإنتاج، CORS، لا UI عام، سجل تدقيق للحالة | شبكة المشغل وRBAC أمام الخدمة مطلوبان في النشر |
| تذكير مزيف أو مكرر | spam إشعارات | FK لدعوة حقيقية، عضو فقط، نافذة 15m–30d، `notified_at` claim ذري، إذن Notification صريح | push خارج التطبيق غير منفذ حتى توجد خدمة موافقات |
| ربط تحليلي بالهوية | تتبع مجموعة | HMAC بنطاق `majlis:`/`match:`، لا أسماء/أكواد/contacts في telemetry | تدوير السر يقطع السلسلة ويجب توثيقه بين الأفواج |
| تعيين تجربة متقلب أو متداخل | نتيجة سببية زائفة | مفتاح تثبيت محلي لا يرسل، 50/50 فقط، تجربة P3 واحدة، فشل آمن، وكشف crossover في التقرير | حذف تخزين الموقع يعيد التعيين ويجب استبعاده وفق الخطة المسجلة |
| حذف غرفة يمحو دليلًا | فقد تاريخ/بلاغ مفتوح | `ON DELETE SET NULL` لجلسات المجلس والبلاغات، واختبار retention | closed/dismissed يحذف بعد 180 يومًا |
| استعادة نسخة تكسر الرابط الدائري | فشل DR | FK دائرية deferrable، واستعادة PGlite مستقلة مختبرة مع المجلس والغرفة | WAL/PITR يبقى P2-O01 مؤجلًا |

## إساءة المعدل والسعة

- البروتوكول العام محكوم بـaction bucket، والدردشة تملك cooldown إضافيًا لكل
  `(room, account)`، مع تنظيف bounded لخريطة cooldown.
- الدعوة المجدولة لا ترسل إلى contacts ولا تنشئ fan-out خارجيًا؛ تظهر لأعضاء
  المجلس الموافقين فقط.
- قائمة آخر المجالس محدودة بثمانية، سجل الجلسات بعشرة في العرض، وطابور التشغيل
  بمئة في الطلب.
- البلاغ المفتوح لا يحذف مع الغرفة، لذا يجب مراقبة نمو الطابور وSLA بدل وضع TTL
  يخفي حادثًا غير معالج.

## قبول المخاطر المتبقية

- لا توجد مطابقة عامة فعلية بعد؛ مسار البلاغ جاهز للطاولات العامة المشروطة في
  P5 ولا يبرر فتحها قبل شرط الكثافة.
- إشعار النظام يعمل فقط والتطبيق مفتوح ويملك الإذن. Push/background يحتاج
  موافقة مستقلة وسياسة رموز أجهزة، وهو غير مدعى في P3.
- HMAC يحمي تقارير المنتج من المعرف الخام لكنه ليس anonymization مطلقًا إذا
  سُرب سر الخدمة؛ لذلك يبقى الوصول للبيانات والسر منفصلًا ومقيدًا.
