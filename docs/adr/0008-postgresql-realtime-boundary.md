# ADR-0008: PostgreSQL وحدود النقل اللحظي

- الحالة: مقبول
- التاريخ: 2026-08-28

## القرار

- قاعدة الإنتاج PostgreSQL عبر pool محدود. المعاملة التي تمس غرفة أو مقعدًا
  تستخدم client واحدًا من بدايتها إلى commit/rollback.
- ملفات SQL ذات أرقام متزايدة هي المصدر الوحيد للـschema. يسجل جدول
  `schema_migrations` اسم الملف وبصمته ووقت تطبيقه، ويرفض تعديل هجرة مطبقة.
- حالات المباراة الحية تبقى في ذاكرة مالك الغرفة مع snapshot ودفق أفعال
  قابلين للاستعادة في PostgreSQL. الحسابات، الغرف، المقاعد، الرموز، وسجل
  التدقيق لا تعتمد على ذاكرة العملية وحدها.
- التخزين الذاكري adapter تطوير واختبار، وليس إعداد إنتاج مقبولًا. يبدأ وضع
  `production` بالفشل إن لم يوجد `DATABASE_URL` أو لم تكن TLS مفعلة وفق سياسة
  البيئة.
- النقل WebSocket فوق HTTPS. تعطّل `perMessageDeflate`، يحد `maxPayload`،
  وتستخدم ping/pong لكشف الاتصال الميت. المصادقة ورسالة `hello` لها مهلة قصيرة
  قبل قبول بقية الأنواع.
- REST يقتصر على الصحة، إنشاء/ترقية الحساب، الحذف، وعمليات لا تحتاج قناة
  لحظية. أفعال المباراة لا تملك مسار HTTP موازٍ يمكنه تجاوز التسلسل.

## النسخ والاستعادة

هناك مستويان مختلفان ولا يجوز الخلط بينهما:

1. تصدير منطقي مشفر للحسابات/المجالس/الأفعال لاختبار سلامة التطبيق
   والاستعادة في بيئة معزولة.
2. نسخ PostgreSQL تشغيلي مع WAL/PITR تديره بيئة النشر، ويختبر دوريًا على قاعدة
   منفصلة مع تسجيل RPO وRTO.

اختبار المستوى الأول جزء من P2 المحلي. اختبار PITR الحقيقي لا يمكن ادعاؤه
دون بيئة PostgreSQL مُدارة، لذلك يبقى بند إطلاق مسجلًا بصراحة في سجل التحقق.

## الاحتفاظ والحذف

- رموز الاستعادة: بصمات فقط، تنتهي خلال 30 ثانية أو عند التدوير.
- idempotency: 24 ساعة ثم حذف آمن بعد انقضاء نافذة إعادة الإرسال.
- سجل أفعال المباراة: 30 يومًا افتراضيًا للتحقيق ثم تجميع/حذف، ما لم توجد
  مطالبة نزاع معلنة.
- telemetry الخام: 30 يومًا؛ المجاميع منزوعة الهوية وفق سياسة القياس.
- حذف الحساب يلغي الجلسات والرموز فورًا، ويفصل سجلات اللعب المحتفظ بها عن
  المعرّف الشخصي. لا تعد النسخ الاحتياطية بحذف لحظي؛ تنتهي وفق دورة النسخ ولا
  يعاد منها حساب محذوف عند الاستعادة.

## سبب عدم اختيار SQLite للإنتاج

SQLite ممتازة للتطوير الأحادي، لكن مالك غرفة متعدد النسخ وسجل أفعال متزامن
يحتاجان معاملات وتنسيقًا وتشغيلًا لا نريد إعادة تصميمه بعد الإطلاق. لذلك لا
نضع قاعدة مؤقتة في طريق الإنتاج ثم نسمي ترحيلها لاحقًا “تحسينًا”.
